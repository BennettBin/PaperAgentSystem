## 1. 审计结论

当前系统已经具备完整工程链路，但不能将“功能存在”“fixture 通过”直接表述为 Agent
算法效果：

- Runtime 具有状态、预算、取消、幂等和 Trace 边界，工程基础可靠。
- 当前 `Planner.create` 仍以一个 Skill 加预先给定 Tool 列表生成计划，不是任务特定的
  LLM 动态规划。
- 当前 `Planner.replan` 主要修改失败步骤的 action 描述，尚未切换 Tool、检索策略或
  证据获取路径。
- `ReActSelfRAGController` 是一次有界的 `clarify/retrieve/answer` 决策，不是多轮自由
  ReAct trajectory。
- 多 Agent 已有父子 Task、Celery Group、并发、取消和部分失败语义，但业务角色主要为
  同构 `paper_reader_agent`，尚无 Critic/Writer/Verifier 协作协议。
- Memory、RAG、Citation、Workspace 隔离和 K04 section scope 已有实现与回归测试。
- J02 训练仍缺少达到门槛的审核数据与正式训练产物；不能宣称 LoRA/SFT 已完成。
- 现有评测大量属于 `unit_fake`、`integration_real` 或产物存在性检查。真实模型 Baseline
  必须在 L02～L05 的冻结数据集上重新运行。

## 3. 冻结 Baseline

| ID | 名称 | 冻结行为 | 用途 |
|---|---|---|---|
| `b0_vanilla_rag` | Vanilla RAG | 一次混合检索后由 4B 直接回答 | 最小 RAG 基线 |
| `b1_fixed_workflow` | Fixed Workflow | 规则路由、固定检索—回答—验证 | 工程工作流基线 |
| `b2_bounded_react` | Current Bounded ReAct | 1.7B 单步决策、4B 回答 | 当前产品基线 |
| `b3_full_4b` | Full 4B | 路由和回答均用 evaluation 4B | 质量/成本上界参考 |

四套 YAML 均由 Pydantic `extra=forbid` 加载，包含模型 Profile、路由、规划、检索、验证、
步骤预算、Prompt 版本和 truth-class 门禁。`paperagent-eval --baseline <ID>` 使用同一
`EvaluationRunner`，并将 baseline ID/kind/config hash 写入报告 metadata。

当前 CLI 对 Baseline 的运行只证明配置可选择和报告可复现；在 L04 接入 case executor、
在 L05 跑真实冻结数据前，不产生任何 Baseline 效果结论。
